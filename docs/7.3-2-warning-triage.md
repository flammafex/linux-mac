# Linux 7.3-2 boot warning triage

Read-only investigation on 2026-11-07, MacPro6,1 with two FirePro D700s,
installed kernel and headers `linux-macpro61` 7.3-2 (`7.3.0-macpro61`).
No drivers were unloaded, mitigations disabled, or boot settings changed.

## apple_gmux: oversized maximum brightness

The boot journal reports indexed gmux version 4.0.11 and a WARN at
`drivers/platform/x86/apple-gmux.c:884`. The source in the 7.3 tarball tests
`props.max_brightness > GMUX_MAX_BRIGHTNESS`, emits `WARN_ON()`, and clamps
the value before registering the backlight device. The live
`/sys/class/backlight/gmux_backlight/max_brightness` is 16777215 (the clamp).
Registration is evidence of the code path, not proof of useful brightness
control on an external monitor.

This is a recoverable firmware/I/O-value warning, not a failed GPU probe.
Both GPUs bind to amdgpu and provide accelerated OpenGL; the current cold
boot started the login manager at 11 seconds and the desktop at 21 seconds.
There is no evidence connecting this warning to the earlier login failure.
The reason the device reports an oversized value remains unresolved.

Disposition: known issue pending upstream/hardware-specific investigation.
Do not simply remove the WARN to claim a fix, or blacklist gmux without
testing its other responsibilities and the resulting system behavior.
Neither changing log severity nor removing the driver establishes that the
underlying value is correct. A prospective fix needs a new-kernel cold boot,
comparison of GPU/display behavior, and verification of the intended gmux
behavior; this triage does not provide that evidence.

## Broadcom wl: return-thunk mitigation incompatibility

The boot journal explicitly warns that broadcom-wl is unmaintained and
incompatible with kernel security mitigations, followed by an unpatched
return-thunk warning at `wl_pci_probe`. Kernel return-thunk mitigation is
enabled. DKMS reports broadcom-wl 6.30.223.271 installed for the running
kernel, and `modinfo -F vermagic wl` matches `7.3.0-macpro61`. The adapter
is using wl and its link is up; these facts do not demonstrate security
mitigation coverage or sustained network reliability.

The installed package's `/usr/src/broadcom-wl-6.30.223.271/Makefile:158-171`
explains that the embedded proprietary blob does not satisfy current
objtool requirements, including security features, and disables objtool
for the combined `wl.o`. A successful rebuild with matching headers does
not resolve this binary limitation. The warning is substantive reduced
security assurance, not proof of a particular remotely exploitable flaw.

Disposition: unresolved third-party driver limitation and release caveat.
Do not disable kernel mitigations or suppress the warning as a fix. The
clean alternative is a supported network path (for example Ethernet or
supported replacement Wi-Fi hardware). Removing wl requires explicit user
approval and an alternate connection; no such change was made. Do not
assume another Broadcom driver supports this exact BCM4360 PCI device.

## Follow-up: intermittent black screen followed by power-off

Later on 2026-11-07, the user reported intermittent startup attempts where
the screen stays black, then the machine powers itself off: the power LED
goes out and the fan stops without power-button intervention. A subsequent
cold-start attempt can succeed. This is a reported full-system power-off,
not merely an absent graphical login, and remains unexplained.

Initially the behavior appeared specific to OpenCore/OCLP for both installed
Linux and the live USB. Subsequent successful startup after shutdown/retry
showed that this is intermittent; a deterministic OpenCore-only failure is
not established. Neither OpenCore nor either warning above is a confirmed
cause. Separately, a diagnostic entry explicitly used
`systemd.unit=multi-user.target`; its inactive display manager was expected
and does not explain a spontaneous power-off. A later regular boot omitted
that override.

Available retained journals do not identify the reported spontaneous event.
The most recent inspected prior boot records `sudo /usr/bin/shutdown` from
tty1, followed by an orderly logind/systemd poweroff. Other inspected boots
also have orderly shutdown endings; those records must not be presented as
evidence explaining the reported incident. No panic, thermal-critical event,
or AMDGPU reset/timeout was found in the inspected prior boot, but that boot
is not an identified incident capture. Its moderate temperatures do not rule
out a thermal event during a different attempt.

The user checked both `/sys/fs/pstore` and `/var/lib/systemd/pstore` with
sudo; both were empty. This establishes only that no persistent crash record
was available there, not that no crash or hardware power-off occurred.

The November 7 live-ISO test archive independently records a successful
7.3-2 session with accelerated OpenGL, RADV enumeration, active macfanctld,
and no failed systemd units. It does not capture a failing attempt or prove
boot-path independence, sustained stability, or installer correctness.

Disposition: treat spontaneous startup power-off as an unresolved stability
blocker, separate from the recovered gmux warning and wl mitigation caveat.
Before another controlled reproduction, establish whether Linux visibly
starts on a failing attempt and the approximate time to power-off. Preserve
incident-time logs if available. Do not claim a graphics-only cause or make
further speculative boot/driver changes from successful-boot logs alone.

## Release decision

Neither warning prevented this boot, but neither has been fixed by triage.
The gmux warning can be documented as a recovered condition with unknown
underlying cause. A release relying on wl must disclose its mitigation
limitation rather than claim an entirely warning-free or fully mitigated
system. These findings do not establish general release stability. The later
reported spontaneous startup power-off blocks a stable-release sign-off
until its cause and impact are understood; successful retries do not resolve
it.
